# Ревью Pull/Merge Request

## Термины

- **Request** — общее название для Pull Request, Merge Request и аналогичных сущностей.
- **PR** — термин GitHub.
- **MR** — термин GitLab.

## Когда использовать

Когда пользователь просит проверить PR/MR/request, провести ревью текущей ветки или оставить комментарии в hosting-системе.

## Выбор режима

### Режим A: передан URL request

Загрузи метаданные и diff request через доступный provider-инструмент.

### Режим B: URL не передан

Проведи локальное ревью diff текущей ветки относительно базовой ветки.

Базовая ветка по умолчанию — `main`, если пользователь или репозиторий не указывает другую.

## Выбор инструмента

Определи provider по URL request или `git remote get-url origin`.

Затем выбери доступный инструмент:

1. MCP/plugin текущей AI-среды для provider.
2. CLI provider:
    - GitHub: `gh`
    - GitLab: `glab`
3. REST API provider, если токен уже настроен и безопасен.
4. Local fallback: `git diff` и отчёт в чат без публикации inline-комментариев.

Если пользователь дал URL request, но нет инструмента для загрузки diff, не подменяй задачу локальным ревью без согласования. Скажи, какой доступ или инструмент нужен, и предложи fallback.

## Подготовка правил

Перед ревью обязательно прочитай:

- `.agents/skills/code-review/SKILL.md`
- `.agents/skills/architecture/SKILL.md`
- `.agents/skills/typescript/SKILL.md`
- `.agents/skills/naming/SKILL.md`
- `.agents/skills/react-components/SKILL.md`
- `.agents/skills/styling/SKILL.md`
- `.agents/skills/testing/SKILL.md`
- `.agents/skills/storybook/SKILL.md`
- `.agents/skills/performance/SKILL.md`

Каждое замечание должно ссылаться на конкретное правило или раздел чек-листа.

## Режим A: request по URL

### 1. Получение метаданных

Извлеки:

- title и description;
- source branch и target branch;
- author;
- changed files;
- diff refs или commit SHAs, если нужны для inline-комментариев.

### 2. Получение diff

Исключай файлы, которые обычно не требуют ручного ревью:

```text
package-lock.json
yarn.lock
pnpm-lock.yaml
node_modules/**
dist/**
coverage/**
```

Если diff слишком большой, приоритизируй:

1. `.ts` и `.tsx`;
2. `.css`, `.scss`;
3. конфиги сборки и тестов;
4. документацию и прочие файлы.

### 3. Анализ

- Анализируй только добавленные и изменённые строки, но учитывай окружающий контекст.
- Не комментируй удалённый код.
- Не дублируй замечания: если проблема системная, оставь одно хорошо сформулированное замечание и укажи масштаб.
- Разделяй блокирующие проблемы и рекомендации.

Классификация серьёзности:

| Severity   | Когда использовать                                      |
| ---------- | ------------------------------------------------------- |
| critical   | баг, потеря данных, уязвимость, поломка сборки          |
| major      | архитектурное нарушение, неверная типизация, регрессия  |
| minor      | локальная проблема качества, читаемости или доступности |
| suggestion | необязательное улучшение                                |

### 4. Публикация inline-комментариев

Если provider-инструмент поддерживает inline-комментарии, публикуй их к конкретным строкам diff.

Формат комментария:

```markdown
**[severity]** Короткое название проблемы

Почему это проблема и как исправить.

Правило: `раздел чек-листа или skill`
```

Для GitHub через `gh` прямые inline-комментарии могут быть недоступны в простом CLI. В этом случае:

1. Сформируй review body со списком замечаний.
2. Если доступен API GraphQL/REST или MCP — используй inline.
3. Если inline недоступен — оставь summary comment или верни отчёт в чат.

### 5. Итоговый комментарий

После inline-комментариев опубликуй или подготовь summary:

```markdown
## Итоги ревью

Request: <title>
Файлов проверено: <count>

| Severity   | Кол-во |
| ---------- | ------ |
| critical   | 0      |
| major      | 0      |
| minor      | 0      |
| suggestion | 0      |

### Главное

Краткое резюме: что блокирует merge и что можно улучшить позже.
```

Если замечаний нет, явно скажи, что блокирующих проблем не найдено, и укажи остаточные риски или непроверенные области.

## Режим B: локальное ревью текущей ветки

### 1. Сбор diff

```bash
git status --short --branch
git diff <base_branch>...HEAD --stat
git diff <base_branch>...HEAD
```

Если есть незакоммиченные изменения, учти их отдельно:

```bash
git diff --stat
git diff
```

### 2. Анализ

Применяй тот же чек-лист, что и для request по URL. Смотри только изменённые строки и ближайший контекст.

### 3. Отчёт

Сначала выведи findings по убыванию серьёзности, затем вопросы и краткое резюме. Если замечаний нет, скажи это явно.

## GitHub-адаптер

### Полезные команды `gh`

```bash
gh pr view <url-or-number> --json title,body,headRefName,baseRefName,author,files,commits
gh pr diff <url-or-number>
gh pr comment <url-or-number> --body-file <summary_file>
```

Для inline review через GitHub может потребоваться GraphQL/REST API или MCP-инструмент. Если текущая среда не даёт безопасного способа опубликовать inline-комментарии, подготовь markdown-отчёт и не имитируй публикацию.

## GitLab-адаптер

### Полезные команды `glab`

```bash
glab mr view <url-or-number>
glab mr diff <url-or-number>
glab mr note <url-or-number> --message "<summary>"
```

Для inline-комментариев используй provider API/MCP, если он доступен.

## Обработка ошибок

- Нет доступа к request: сообщи, что нужны права или авторизация provider CLI/MCP.
- Provider не распознан: предложи локальное ревью diff или попроси пользователя передать diff.
- Diff слишком большой: предупреди о приоритизации и проверь самые рискованные файлы.
- Невозможно опубликовать inline-комментарий: опубликуй summary или верни отчёт в чат.
- CI/линтеры недоступны: укажи, какие проверки не удалось выполнить.

## Важно

- Ревью должно вести к конкретным действиям, а не к вкусовым замечаниям.
- Не публикуй секреты из diff.
- Не оставляй комментарии к строкам, которых нет в diff.
- Не повторяй одно и то же замечание десятки раз.
- В финальном сообщении всегда разделяй опубликованные комментарии и локально найденные, но не опубликованные замечания.
