# Архитектура приложения и фич

## Базовый принцип

Шаблон не навязывает сложную архитектуру на старте. Сначала используй простую структуру `src/`, затем выделяй общие слои и фичи, когда появляется реальная потребность.

## Верхнеуровневые зоны

- **App** — инициализация приложения: провайдеры, роутинг, глобальная конфигурация. Зависимости тянутся в App, но не из него. Не складывай сюда переиспользуемые сущности.
- **Common или shared-слой** — компоненты, хуки, утилиты, стили и сервисы без продуктовой специфики. Правило проверки: сущность можно вынести во внешнюю библиотеку без знания домена.
- **Core или domain-слой** — бизнес-сущности, общие для нескольких несвязанных фич. Создавай только когда такая общая бизнес-логика действительно появилась.
- **Feature** — самостоятельная продуктовая область. Фича содержит всё, что относится к её сценарию: компоненты, хуки, доменные типы, сервисы, тесты и stories.

Если проект уже выбрал конкретный вариант расположения (`src/features/FeatureName`, `src/FeatureName` или другой), сохраняй его и не смешивай подходы без отдельного решения.

## Структура фичи

```text
FeatureName/
├── __fixtures__/         # генераторы данных для тестов и историй
├── __stories__/          # истории Storybook, если они не лежат рядом с компонентами
├── __tests__/            # интеграционные тесты фичи
├── components/           # UI-компоненты фичи
├── contexts/             # React-контексты
├── domain/               # доменная модель, типы, бизнес-правила
├── hooks/                # прикладные сценарии и эффекты
├── services/             # API-клиенты и доступ к данным
├── utilities/            # утилиты слоя отображения
└── index.ts              # публичный API фичи
```

Если файл определённого типа один, папку под него можно не заводить:

```text
FeatureName/
├── EntityName.entity.ts
├── FeatureName.tsx
├── FeatureName.utilities.ts
├── useFeatureName.ts
└── index.ts
```

## Доменная модель

Доменная модель — чистый TypeScript без зависимостей от React. В ней живут интерфейсы сущностей, value objects, константы, перечисления и бизнес-правила.

```ts
export type TEntityId = Brand<number, 'EntityId'>;

export interface IEntity {
    id: TEntityId;
    name: string;
}

export function isValidEntity(entity: IEntity): boolean {
    return entity.name.trim().length > 0;
}
```

Именование файлов доменной модели: `*.entity.ts`.

## Сервисы и DTO

- API-клиенты размещай в `services/` или файлах `*.apiClient.ts`.
- Не вызывай сервисы напрямую из компонентов: используй хуки или прикладный слой фичи.
- Контракты API размещай в `*.dto.ts`.
- Адаптеры `*.adapter.ts` добавляй только когда нужно преобразовать DTO в доменную сущность.

```text
dtos/
├── entity.dto.ts
└── entity.adapter.ts
```

## Компоненты

- Компоненты фичи лежат в `components/`.
- Для сложных сценариев разделяй подготовку данных и отображение:
    - `*Presenter` — данные, хуки, состояния загрузки и ошибок
    - `*View` — разметка и пользовательские события
    - `*Routes` — роутинг фичи, если он есть
- Для простых компонентов не вводи Presenter/View искусственно.

## Контекст вместо prop drilling

Если родитель прокидывает много пропсов в глубокое дерево, введи контекст в рамках фичи. Экспортируй только провайдер и хук доступа к контексту.

## Реэкспорты

В каждой папке, которая отдаёт сущности наружу, добавляй `index.ts`.

- Экспортируй только то, что реально используется за пределами папки.
- Не оставляй неактуальные реэкспорты.
- Не делай реэкспорт из старого места "для совместимости" при переносе сущности: обновляй импорты напрямую.

## Модель взаимодействия

```
Пользователь → Тупые компоненты → Презентеры → Хуки → Сервисы → HTTP → API
                                                ↕
                                             Состояние
Все слои могут обращаться к Domain (entities) за типами и бизнес-логикой.
```

Все слои могут использовать domain-типизацию и чистую бизнес-логику. Domain не зависит от React, UI и сетевого слоя.

## Правило размера файла

- Файлы с кодом больше 300 строк, кроме фикстур, историй и тестов, стоит разбивать на части.
- Для тестов ориентир — до 550 строк.
- Небольшой компонент фичи с простой разметкой можно оставить в месте применения, если вынос не улучшает читаемость.

## FAQ: куда класть

- Общий UI без бизнес-логики -> `components/`, `Common/components/` или выбранный shared-слой проекта.
- Переиспользуемый хук без бизнес-логики -> `hooks/`, `Common/hooks/` или выбранный shared-слой.
- Бизнес-сущность одной фичи -> `FeatureName/domain/`.
- Бизнес-сущность нескольких несвязанных фич -> `Core/` или выбранный domain-слой.
- API-запросы -> `services/` или `*.apiClient.ts`.
- Тесты -> рядом с файлом или в `__tests__/`, согласно существующему стилю проекта.
- Истории -> рядом с компонентом или в `__stories__/`, согласно существующему стилю проекта.
