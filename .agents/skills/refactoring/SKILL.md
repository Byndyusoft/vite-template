# Рефакторинг

## Порядок действий

Если пользователь просит исправить замечания из Pull/Merge Request и передаёт URL request, используй [refactor-pull-request](../refactor-pull-request/SKILL.md).

1. Прочитай релевантные правила проекта:
    - `architecture/SKILL.md`
    - `typescript/SKILL.md`
    - `naming/SKILL.md`
    - `react-components/SKILL.md`
    - `testing/SKILL.md`
    - `storybook/SKILL.md`
    - `styling/SKILL.md`
    - `performance/SKILL.md`
    - `documentation-update/SKILL.md`
2. Определи scope задачи. Если пользователь не указал scope, анализируй diff текущей ветки относительно базовой.
3. По умолчанию базовая ветка — `main`, если пользователь или репозиторий явно не задаёт другую.
4. Исправляй только реальные проблемы: баги, нарушения архитектуры, типизации, тестов, доступности, производительности или явную мёртвую сложность.
5. Не добавляй крупные переписывания сверх задачи.
6. После правок запускай релевантные проверки из `package.json`.
7. Обновляй документацию по матрице из `documentation-update/SKILL.md`, если рефакторинг меняет публичные соглашения, скрипты, env-переменные или архитектуру.

## Что считать хорошим рефакторингом

- Поведение сохранено или улучшено согласно задаче.
- Код стал проще читать и тестировать.
- Убраны дубли и мёртвый код.
- Импорты указывают на актуальные места без legacy-реэкспортов.
- Тесты закрывают изменённую сложную логику.

## Перенос сущностей

При переносе сущности в другое место не создавай реэкспорт в прежнем файле для обратной совместимости. Обнови импорты напрямую.

## Prop drilling

Если компонент прокидывает много пропсов через несколько уровней, оцени контекст фичи или композицию через `children`. Не вводи контекст ради двух пропсов.

## Примеры использования

```text
/refactoring
/refactoring main
отрефактори компонент формы регистрации
исправь замечания локального ревью в текущей ветке
```
