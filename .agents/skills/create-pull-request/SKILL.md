# Создание Pull/Merge Request

## Термины

- **Request** — общее название для Pull Request, Merge Request и аналогичных сущностей.
- **PR** — термин GitHub.
- **MR** — термин GitLab.

В пользовательских сообщениях сохраняй терминологию платформы, но в алгоритме ниже используй нейтральное слово request.

## Когда использовать

Когда пользователь просит создать PR/MR/request для текущей ветки, подготовить описание PR или запушить ветку и открыть request.

## Режимы работы

### Обычный режим

Создаёт один request со всеми изменениями ветки относительно целевой ветки.

### Режим `--split-shared-and-task`

Разделяет изменения на два request:

1. **Shared request** — общие изменения проекта: shared/common-код, конфиги, инфраструктура, документация.
2. **Task request** — feature-специфичный код задачи.

Ключевой принцип: shared-ветка после отделения должна быть работоспособна сама по себе.

## Выбор инструмента

Сначала определи provider по `git remote get-url origin`.

| Remote содержит             | Provider  |
| --------------------------- | --------- |
| `github.com` или GitHub URL | GitHub    |
| `gitlab.com` или GitLab URL | GitLab    |
| `bitbucket.org`             | Bitbucket |
| другое                      | Generic   |

Затем выбери доступный инструмент в таком порядке:

1. Специализированный MCP/plugin текущей AI-среды, если он доступен для provider.
2. CLI provider в shell:
    - GitHub: `gh`
    - GitLab: `glab`
    - Bitbucket/другое: установленный проектом CLI, если он явно документирован.
3. REST API provider, если токен уже настроен в окружении и это безопасно.
4. Fallback: подготовь заголовок, markdown-описание и команды `git push`, но не создавай request автоматически.

Не требуй конкретный provider в шаблоне. Если доступен только GitHub, используй GitHub-адаптер.

## Алгоритм: обычный режим

### 1. Сбор контекста

Выполни и проанализируй:

```bash
git branch --show-current
git status --short --branch
git remote get-url origin
git log <target_branch>..HEAD --oneline
git diff <target_branch>...HEAD --stat
git diff <target_branch>...HEAD
```

Если целевая ветка не указана, используй `main`. Если в репозитории основной веткой является `master`, `dev` или другая ветка, выбери её по контексту remote/default branch или спроси пользователя.

### 2. Проверки перед созданием

- Если есть незакоммиченные изменения, предупреди пользователя и уточни, включать ли их.
- Если текущая ветка не запушена, запушь её с upstream после согласования или в рамках явной просьбы "запушь и создай request":

```bash
git push -u origin <branch-name>
```

### 3. Шаблон описания

Выбери шаблон в таком порядке:

1. `.github/PULL_REQUEST_TEMPLATE.md`
2. `.gitlab/merge_request_templates/default.md`
3. `.gitlab/merge_request_templates/*.md`, если default отсутствует и выбор очевиден
4. Локальный шаблон проекта, если он документирован в README
5. Универсальный шаблон из этого skill

Универсальный шаблон:

```markdown
## Описание

Кратко: цель и контекст изменений.

## Изменения

- Что было сделано.

## Скриншоты/Видео (если UI)

Не применимо.

## Проверки

- [ ] Линтеры
- [ ] Типизация
- [ ] Тесты
- [ ] Сборка

## Связанные задачи

Нет.
```

### 4. Генерация заголовка и описания

Проанализируй все коммиты и diff ветки, не только последний коммит.

Правила:

- Заголовок короткий, до 72 символов, желательно в стиле Conventional Commits: `type(scope): описание`.
- Описание фокусируется на цели и рисках, а не только на списке файлов.
- Все обязательные разделы выбранного шаблона должны присутствовать.
- Если UI не менялся, в разделе скриншотов укажи "Не применимо" или "Нет UI-изменений".
- Если есть связанные задачи, добавь ссылки или номера.

### 5. Согласование

Перед созданием request покажи пользователю:

- provider и выбранный инструмент;
- source branch;
- target branch;
- заголовок;
- описание.

Спроси, корректны ли target branch, заголовок, описание и связанные задачи.

### 6. Создание request

#### GitHub через `gh`

```bash
gh pr create --base <target_branch> --head <source_branch> --title "<title>" --body-file <body_file>
```

Если нужен draft:

```bash
gh pr create --draft --base <target_branch> --head <source_branch> --title "<title>" --body-file <body_file>
```

#### GitLab через `glab`

```bash
glab mr create --target-branch <target_branch> --source-branch <source_branch> --title "<title>" --description-file <body_file>
```

#### Generic fallback

Если автоматическое создание невозможно:

1. Убедись, что ветка запушена.
2. Выведи пользователю готовые заголовок и описание.
3. Дай прямую ссылку на создание request, если её можно построить из remote URL.
4. Сообщи, какой инструмент отсутствует или не настроен.

### 7. Результат

После успешного создания выведи:

- URL request;
- заголовок;
- source branch и target branch;
- статус draft/ready, если он известен.

## Алгоритм: `--split-shared-and-task`

### 1. Сбор изменённых файлов

```bash
git diff <target_branch>...HEAD --name-only
git log <target_branch>..HEAD --format="%H %s" --reverse
```

### 2. Классификация файлов

Классифицируй каждый файл как shared, task или needs-human.

**Shared**:

- общие компоненты, хуки, утилиты, стили;
- конфиги проекта (`*.config.*`, `tsconfig*.json`, `package.json`, lock-файлы);
- CI/CD и hosting-конфиги;
- Storybook/Vitest/ESLint/Stylelint/Prettier настройки;
- корневая документация, если она описывает общий процесс или инфраструктуру.

**Task**:

- код конкретной фичи;
- assets, стили, stories и тесты, относящиеся только к фиче;
- документация конкретной фичи.

**Needs-human**:

- файлы, смысл которых нельзя понять по пути;
- изменения, которые смешивают инфраструктуру и feature-код;
- файлы, где shared-часть зависит от task-части.

### 3. Согласование классификации

Покажи пользователю два списка:

```text
SHARED:
- path/to/file

TASK:
- path/to/file

NEEDS HUMAN:
- path/to/file
```

Продолжай только после согласования, если есть `NEEDS HUMAN` или классификация неочевидна.

### 4. Edge cases

| Сценарий                   | Действие                                     |
| -------------------------- | -------------------------------------------- |
| Все файлы shared           | Создай один shared request                   |
| Все файлы task             | Создай один task request                     |
| Shared-файлов очень мало   | Спроси, стоит ли разделять                   |
| Shared-ветка ломает проект | Переклассифицируй зависимости или остановись |

### 5. Создание веток

Создай shared-ветку от target branch и перенеси в неё только shared-изменения. Затем создай task-ветку от shared-ветки и перенеси task-изменения.

Сохраняй осмысленные коммиты, если это возможно. Если точное восстановление коммитов слишком рискованно, согласуй с пользователем более простой вариант.

### 6. Верификация

Для shared-ветки запусти релевантные проверки последовательно:

```bash
npm run eslint:check
npm run typescript:check
npm run test:check
npm run stylelint:check
npm run prettier:check
npm run build
```

Список команд адаптируй к `package.json`.

### 7. Создание двух request

Создай:

1. Shared request: `<shared_branch>` -> `<target_branch>`
2. Task request: `<task_branch>` -> `<shared_branch>`

В описании task request укажи зависимость от shared request. В описании shared request укажи связанный task request, если его URL уже известен.

## Обработка ошибок

- Provider не распознан: используй generic fallback.
- CLI не установлен: проверь наличие MCP/plugin/API; если их нет, подготовь описание и команды.
- Нет прав или токена: сообщи, какой доступ нужен, и не публикуй токены в чат.
- Remote URL не поддерживается: попроси пользователя дать URL репозитория или создай только markdown-описание.
- Diff слишком большой: сначала сформируй summary/stat, затем читай приоритетные файлы.

## Важно

- Не создавай request без согласования заголовка и описания, если пользователь не попросил явно полностью автономный режим.
- Не публикуй секреты из diff в описание request.
- Не меняй целевую ветку молча.
- Используй шаблон проекта, если он есть.
- Если request создан успешно, верни пользователю ссылку.
